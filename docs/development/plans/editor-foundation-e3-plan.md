## Purpose and phase exit

Turn the E0 editor UI foundation into a coherent application shell that later
tools can extend without changing central dispatch code. The completed phase has:

- deterministic, statically compiled extension discovery, activation and reverse
  teardown;
- one contextual command path shared by menus, buttons and shortcuts;
- stable panel types and instances in docked or detached hosts;
- declarative menu, toolbar and context-menu contributions;
- bounded diagnostics, progress and status presentation;
- versioned layout and user-preference persistence; and
- a separately registered demonstration extension proving the shell rather than
  a hard-coded tool.

This remains editor/tooling infrastructure. Runtime products do not initialize
the editor shell, read editor layouts or load editor extensions.

## Existing owners that E3 must extend

- `EditorApplication` composes the one `EngineHost` and application state machine.
  E3 must not add another application loop or service container.
- `EngineHost` owns dependency validation, startup, rollback and reverse shutdown
  for services. Extension lifetime must be represented beneath that owner.
- `ProjectWorkspaceService` owns the validated `.vproject`, its configured roots
  and project lifetime. Its `plugins` list is selection/configuration input, not
  permission to scan or load arbitrary native libraries.
- `EditorUiService` owns the ImGui context, editor frame, native UI hosts, textures
  and the existing `EditorPanelRegistry`. E3 must extend that panel registry rather
  than introduce a competing panel store.
- Window, input, presentation, rendering and frame-pipeline services keep their E0
  authority. Extensions never create an alternate event pump, swap chain, command
  submission path or render scheduler.
- Diagnostics remains the log producer. E3 presents a bounded view of diagnostics;
  it does not become a second logger.
- Domain systems retain command behavior. The E3 command layer routes an intent to
  the current receiver; it does not absorb asset, world, document or renderer
  implementation.

## Cross-subphase invariants

1. All shell registry mutation and extension activation/deactivation occur on the
   editor main-thread owner and outside an active `EditorUiService` frame.
2. Stable technical identities are distinct from display text. Persist IDs, not
   translated labels, pointers, array positions or ImGui window names.
3. Every contribution has one owning extension. Partial activation and ordinary
   teardown remove owned contributions in reverse dependency/order before the
   extension state or referenced service disappears.
4. Registries are bounded, reject duplicate identities and return explicit failure.
   Allocation failure cannot leave a partially visible extension.
5. `.vproject` selects only descriptors compiled into the executable. E3 adds no
   dynamic DLL ABI, directory code loading, hot unload, scripting or marketplace.
6. Direct APIs perform requests. Typed, removable subscriptions may report state
   changes; E3 does not introduce a universal message bus.
7. UI callbacks perform bounded presentation and request submission. Long asset,
   filesystem, build or renderer work stays with its existing asynchronous owner.
8. Text/IME capture, contextual shortcut routing and viewport navigation cannot
   consume the same input event.
9. Layout and user preferences live under Saved/user state. Authored project policy
   remains in `.vproject` or explicit project configuration. A layout file is never
   an authored asset or an E1F transaction.
10. EngineHost reverse-dependency quiesce applies: a dependent service may perform its
    explicitly bounded final capture through still-live owners before those owners quiesce.
    Once `EditorShellService` quiesce begins, it stops new shell callbacks before shell-owned
    registrations are revoked. Teardown removes subscriptions, panels and other registrations
    before `EditorUiService` and workspace services shut down. No callback may retain an
    extension after its owner is inactive.
11. E3 uses Premake and focused generated Visual Studio projects. Compilation,
    linkage, automated tests, native UI observation and source review remain
    separate validation claims.

## E0 and E2 boundary

E0A-E0E supply the accepted source architecture and E0F supplies a working native
two-host proof. E3.1 and E3.2 can build on those established contracts. E3.3 must
not close its real docking/focus behavior until E0F's remaining interactive
drag/redock, mixed-DPI and minimized-host checks are either passed or replaced by
equally strong current evidence. E3 does not silently relabel an open E0F check as
complete.

E2 is a parallel backend track. E3.5 may later adapt E2 status into shell progress
and diagnostics, and later asset tools may issue E2 requests through its public
surface. No E3 subphase may depend on `assetStreaming` implementation headers or
move E2 orchestration into the editor executable.
