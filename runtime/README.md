# Runtime client

`runtime` is a top-level product client, not an engine module. It owns `RuntimeApplication` and a native entry slice for each supported platform. The Windows slice is a windowed executable with a native `wWinMain` entry and enters the framework through the Windows adapter.

Normal startup follows two explicit application states: `startupSession` and `running`. Resource Streaming mounts the canonical `DATA000.vpak` package set from the configured runtime root during service initialization, before renderer/world consumers start. `startupSession` supplies the validated boot record's typed world and input references to World Session. World loading remains asynchronous. After the `vworld`, grid and executor are ready, the session initializes the Flecs Game World and enters `running`; cells and drawable resources continue their normal asynchronous progress.

Development uses the `bootstrapImage` tool to cook and atomically publish a minimal normal game image into `bin/Runtime/<Config>`, beside `Vanguard.exe`. Runtime uses its executable directory as the immutable game root. Editor requires an explicit `.vproject` argument and uses that file's parent directory as its project root; neither application treats the engine repository as application data. Libraries, tests, PDBs, and other internal products live under `build/output/<Config>` rather than polluting deployable application directories.

On entry to `running`, the application compiles the managed Frame Pipeline after every service has registered its participants. Each running tick executes one timed frame through the fixed global phases. Game World participates in `Simulation` and receives the pipeline's variable simulation delta. On exit, the state requests World Session stop and polls it. Stopping a session preserves process sources; Resource Streaming unmounts them after dependent services shut down. World-switch states use the same stop/start transaction with explicit input choices. `--validate-bootstrap` deliberately omits package mounting and exits before executing a content frame, allowing native entry-point and service-graph validation without a cooked game image.
